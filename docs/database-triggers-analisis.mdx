### 2.1 Triggers de `updated_at` (Migración 001 y 014)

Estos triggers se disparan BEFORE UPDATE en cada tabla para mantener la columna `updated_at` actualizada automáticamente.

```sql
CREATE OR REPLACE FUNCTION update_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

**Tablas con trigger `updated_at`:** users, clients, categories, products, inventory, purchases, sales, invoices, system_config, brands, price_lists, warehouses, companies, goods_receipts, quality_inspections, checkout_sessions, coupons, returns, account_plans, accounting_entries, ncf_sequences, taxpayer_info, payment_methods, cash_registers.

### 2.2 Trigger de Inventario desde Compra (Migración 009)

```sql
CREATE OR REPLACE FUNCTION update_product_cost_from_purchase()
RETURNS TRIGGER AS $$
BEGIN
  -- Actualiza cost_price del producto
  UPDATE products SET cost_price = NEW.unit_price WHERE id = NEW.product_id;

  -- Inserta/actualiza inventario
  INSERT INTO inventory (product_id, warehouse, stock)
  VALUES (NEW.product_id, 'principal', NEW.quantity)
  ON CONFLICT (product_id, warehouse)
  DO UPDATE SET stock = inventory.stock + NEW.quantity;

  -- Registra movimiento
  INSERT INTO inventory_movements (product_id, warehouse, type, quantity,
    previous_stock, new_stock, reference_type, reference_id, reason, user_id)
  VALUES (NEW.product_id, 'principal', 'entry', NEW.quantity, 0, 0,
    'purchase', NEW.purchase_id, 'Entrada por compra',
    (SELECT user_id FROM purchases WHERE id = NEW.purchase_id));

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_purchase_item_update_inventory
  AFTER INSERT ON purchase_items
  FOR EACH ROW
  EXECUTE FUNCTION update_product_cost_from_purchase();
```

### 2.3 Trigger de Descuento de Stock por Venta (Migración 009, modificado en 016)

**Trigger CRÍTICO para el flujo de ventas.** Descuenta inventario cuando se crea un ítem de venta.

```sql
CREATE OR REPLACE FUNCTION decrease_stock_from_sale()
RETURNS TRIGGER AS $$
DECLARE
  v_current_stock INTEGER;
BEGIN
  -- Obtener stock actual
  SELECT stock INTO v_current_stock
  FROM inventory
  WHERE product_id = NEW.product_id AND warehouse = 'principal';

  IF NOT FOUND THEN
    RAISE EXCEPTION 'Producto % sin inventario', NEW.product_id;
  END IF;

  IF v_current_stock < NEW.quantity THEN
    RAISE EXCEPTION 'Stock insuficiente para %: disponible %, requerido %',
      NEW.product_name, v_current_stock, NEW.quantity;
  END IF;

  -- Descontar stock
  UPDATE inventory
  SET stock = stock - NEW.quantity,
      movement_date = NOW(),
      updated_at = NOW()
  WHERE product_id = NEW.product_id AND warehouse = 'principal';

  -- Registrar movimiento de salida
  INSERT INTO inventory_movements (product_id, warehouse, type, quantity,
    previous_stock, new_stock, reference_type, reference_id, reason, user_id)
  SELECT
    NEW.product_id, 'principal', 'exit', NEW.quantity,
    v_current_stock, v_current_stock - NEW.quantity,
    'sale', NEW.sale_id, 'Venta realizada', s.user_id
  FROM sales s WHERE s.id = NEW.sale_id;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_sale_item_decrease_stock
  AFTER INSERT ON sale_items
  FOR EACH ROW
  EXECUTE FUNCTION decrease_stock_from_sale();
```

**Cambio en Migración 016:** La razón cambió de `'Salida por venta automática'` a `'Venta realizada'`.

### 2.4 Trigger de Reversión de Stock por Compra Anulada (Migración 009)

```sql
CREATE OR REPLACE FUNCTION revert_inventory_on_purchase_cancel()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.status = 'cancelled' THEN
    UPDATE inventory i
    SET stock = i.stock - pi.quantity
    FROM purchase_items pi
    WHERE pi.purchase_id = NEW.id AND pi.product_id = i.product_id;

    -- Registrar movimiento
    INSERT INTO inventory_movements (product_id, warehouse, type, quantity, ...)
    SELECT pi.product_id, 'principal', 'exit', pi.quantity, ...
    FROM purchase_items pi WHERE pi.purchase_id = NEW.id;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

### 2.5 Trigger de Reversión de Stock por Venta Anulada (Migración 016 - NUEVO)

```sql
CREATE OR REPLACE FUNCTION revert_stock_on_sale_cancel()
RETURNS TRIGGER AS $$
DECLARE
  v_item RECORD;
  v_current_stock INTEGER;
BEGIN
  IF NEW.status = 'cancelled' THEN
    FOR v_item IN
      SELECT product_id, quantity, sale_id FROM sale_items WHERE sale_id = NEW.id
    LOOP
      SELECT stock INTO v_current_stock
      FROM inventory WHERE product_id = v_item.product_id AND warehouse = 'principal';

      UPDATE inventory
      SET stock = stock + v_item.quantity, updated_at = NOW()
      WHERE product_id = v_item.product_id AND warehouse = 'principal';

      INSERT INTO inventory_movements (product_id, warehouse, type, quantity,
        previous_stock, new_stock, reference_type, reference_id, reason, user_id)
      VALUES (v_item.product_id, 'principal', 'entry', v_item.quantity,
        v_current_stock, v_current_stock + v_item.quantity,
        'sale_cancellation', NEW.id,
        'Venta anulada - reversión de inventario', NEW.user_id);
    END LOOP;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_sale_cancel_revert_inventory
  AFTER UPDATE OF status ON sales
  FOR EACH ROW
  WHEN (NEW.status = 'cancelled')
  EXECUTE FUNCTION revert_stock_on_sale_cancel();
```

## 3. Bugs Encontrados y Correcciones Aplicadas

### 3.1 Bug: Movimientos de Inventario Duplicados

**Severidad:** 🔴 Crítica
**Síntoma:** Cada venta generaba DOS movimientos de inventario (doble descuento de stock).

**Causa Raíz:** El trigger `trg_sale_item_decrease_stock` (AFTER INSERT ON sale_items) YA descuenta el stock automáticamente. Pero el código de la aplicación (`sale-service`) también llamaba a `updateInventoryStock()` después de crear la venta, causando un doble descuento.

**Solución:** Se eliminaron las llamadas a `updateInventoryStock()` en:
- `CreateSaleUseCase.execute()`
- `CheckoutUseCase.execute()`

El trigger de BD ahora es el único responsable de descontar stock.

**Archivos modificados:** `backend/services/sale-service/src/usecases/index.js`

### 3.2 Bug: Tabla `invoice_items` Nunca Creada

**Severidad:** 🔴 Crítica
**Síntoma:** Error `"Could not find the table 'public.invoice_items' in the schema cache"` al crear facturas.

**Causa Raíz:** La función `autoCreateInvoice()` en sale-service intentaba insertar en `invoice_items`, pero esta tabla nunca fue creada en ninguna migración.

**Solución rediseñada:** En lugar de crear la tabla (requiere DDL en Supabase), se modificó el flujo para que:
1. `autoCreateInvoice()` ya no inserta en `invoice_items` — solo crea la factura
2. `invoice-service` obtiene los ítems dinámicamente desde `sale_items` usando el `sale_id` de la factura

**Ventaja:** No hay duplicación de datos (los items existen una sola vez en `sale_items`).

**Archivos modificados:**
- `backend/services/sale-service/src/usecases/index.js` — eliminado INSERT en `invoice_items`
- `backend/services/invoice-service/src/repository/index.js` — `findById()` ahora consulta `sale_items` en lugar de `invoice_items`

### 3.3 Bug: Violación de UNIQUE CONSTRAINT en NCF

**Severidad:** 🔴 Crítica
**Síntoma:** `"duplicate key value violates unique constraint 'invoices_ncf_key'"` al crear la segunda factura.

**Causa Raíz:** La columna `ncf VARCHAR(50) UNIQUE DEFAULT ''` causaba que PostgreSQL tratara `''` como un valor no-nulo. La segunda factura sin NCF intentaba insertar `''` de nuevo, violando UNIQUE.

**Solución:**
1. En código: Cambiado `ncf: ''` a `ncf: null` en `autoCreateInvoice()`
2. En BD (manual): Ejecutado `UPDATE invoices SET ncf = NULL WHERE ncf = ''`
3. Pendiente en migración 016: Cambiar la constraint UNIQUE por un índice parcial `WHERE ncf IS NOT NULL AND ncf != ''`

**Archivos modificados:**
- `backend/services/sale-service/src/usecases/index.js` — `ncf: null`
- `backend/services/invoice-service/src/domain/index.js` — `this._ncf = ncf || null`
- `database/migrations/016_fix_double_inventory_and_triggers.sql` — Sección 6: DROP CONSTRAINT + partial unique index

### 3.4 Bug: `findById()` en Invoice Service Retornaba 404

**Severidad:** 🟡 Alta
**Síntoma:** `GET /api/v1/invoices/:id` retornaba error 404.

**Causa Raíz:** El método `findById()` usaba `.select('*, invoice_items(*, products(name, sku)), sales(sale_number, status), clients(...)')` con `.single()`. Como `invoice_items` no existía, la consulta fallaba.

**Solución:** Se reescribió para hacer consultas separadas:
1. Fetch invoice + client join
2. Fetch items desde `sale_items` por `sale_id`
3. Fetch sale number

**Archivos modificados:** `backend/services/invoice-service/src/repository/index.js`

### 3.5 Bug: `event.data` vs `event.payload` en Event Bus

**Severidad:** 🟡 Alta
**Síntoma:** `[InMemoryEventBus] Handler failed for sales.sale.created: Cannot read properties of undefined (reading 'sale')`

**Causa Raíz:** La clase `DomainEvent` almacena datos en la propiedad pública `payload` (vía `this.payload = payload`), pero TODOS los subscribers en los 10 servicios usaban `event.data.X`, que es `undefined`.

**Solución:** Se reemplazó `event.data.` por `event.payload.` en los 10 archivos de subscribers.

**Archivos modificados (10):**
- `backend/services/sale-service/src/subscribers/index.js`
- `backend/services/inventory-service/src/subscribers/index.js`
- `backend/services/invoice-service/src/subscribers/index.js`
- `backend/services/notification-service/src/subscribers/index.js`
- `backend/services/payment-service/src/subscribers/index.js`
- `backend/services/procurement-service/src/subscribers/index.js`
- `backend/services/report-service/src/subscribers/index.js`
- `backend/services/user-service/src/subscribers/index.js`
- `backend/services/config-service/src/subscribers/index.js`
- `backend/services/identity-service/src/subscribers/index.js`

### 3.6 Bug: `handler.handle is not a function` en Event Bus

**Severidad:** 🟡 Alta
**Síntoma:** `[InMemoryEventBus] Handler failed for sales.sale.created: handler.handle is not a function`

**Causa Raíz:** `InMemoryEventBus.publish()` itera handlers y llama `handler.handle(event)`, pero `subscribe()` almacena las funciones flecha directamente (sin envolver en objeto `{ handle: fn }`).

**Solución:** Se modificó `InMemoryEventBus.subscribe()` para detectar funciones y envolverlas automáticamente en `{ handle: handler }`.

**Archivo modificado:** `packages/event-bus/src/index.js`

## 4. Mejoras de Rendimiento para Funciones Más Rápidas

### 4.1 Optimización: Reemplazar Función `decrease_stock_from_sale()`

**Problema:** La función realiza 3 queries separados (SELECT, UPDATE, INSERT) por cada ítem de venta.

**Mejora sugerida:** Usar CTE (WITH) para combinar en una sola transacción implícita:

```sql
CREATE OR REPLACE FUNCTION decrease_stock_from_sale()
RETURNS TRIGGER AS $$
BEGIN
  WITH stock_info AS (
    SELECT stock AS current_stock
    FROM inventory
    WHERE product_id = NEW.product_id AND warehouse = 'principal'
    FOR UPDATE  -- Lock row to prevent race conditions
  )
  UPDATE inventory
  SET stock = stock - NEW.quantity,
      movement_date = NOW(),
      updated_at = NOW()
  WHERE product_id = NEW.product_id AND warehouse = 'principal';

  INSERT INTO inventory_movements (product_id, warehouse, type, quantity,
    previous_stock, new_stock, reference_type, reference_id, reason, user_id)
  SELECT NEW.product_id, 'principal', 'exit', NEW.quantity,
    current_stock, current_stock - NEW.quantity,
    'sale', NEW.sale_id, 'Venta realizada', s.user_id
  FROM stock_info, sales s WHERE s.id = NEW.sale_id;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

**Ganancia estimada:** ~30% menos de roundtrips a la BD.

### 4.2 Optimización: Índices Faltantes

Los siguientes índices mejorarían consultas frecuentes:

```sql
-- Consultas de dashboard (agregaciones por fecha)
CREATE INDEX IF NOT EXISTS idx_sales_created_at ON sales(created_at);
CREATE INDEX IF NOT EXISTS idx_inventory_movements_created_at ON inventory_movements(created_at);

-- Consultas de búsqueda de productos
CREATE INDEX IF NOT EXISTS idx_products_name_trgm ON products USING GIN (name gin_trgm_ops);
CREATE INDEX IF NOT EXISTS idx_products_sku_trgm ON products USING GIN (sku gin_trgm_ops);

-- Consultas de auditoría por entidad
CREATE INDEX IF NOT EXISTS idx_audit_logs_entity ON audit_logs(entity, entity_id);

-- Consultas de facturas por estado
CREATE INDEX IF NOT EXISTS idx_invoices_status ON invoices(status);

-- Consultas de movimientos por referencia
CREATE INDEX IF NOT EXISTS idx_inventory_movements_reference ON inventory_movements(reference_type, reference_id);
```

### 4.3 Optimización: Evitar NOTIFICACIONES en Línea

El trigger `notify_purchase_created()` ejecuta INSERT en `user_notifications` en la misma transacción que la compra. Para alto volumen, conviene usar una cola:

- Opción actual: Sincrónico (más simple, consistente)
- Opción mejorada: Usar `pg_notify()` + listener externo para alto volumen

### 4.4 Optimización: Índice Compuesto para Kardex

```sql
-- La consulta de kardex filtra por product_id + referencia
CREATE INDEX IF NOT EXISTS idx_movements_product_reference
  ON inventory_movements(product_id, reference_type, created_at DESC);
```

### 4.5 Mejora: Validación de Stock con `FOR UPDATE`

La función `decrease_stock_from_sale()` actualmente hace SELECT sin lock, luego UPDATE. En condiciones de alta concurrencia, dos ventas simultáneas podrían leer el mismo stock y ambas pasar la validación. Usar `SELECT ... FOR UPDATE` previene race conditions.

## 6. Flujo de Datos: Venta → Factura → Inventario

```
1. POST /api/v1/sales (POS)
   │
   ├─► CreateSaleUseCase.execute()
   │     ├─► Crea Sale + SaleItems (INSERT sales, sale_items)
   │     │     └─► [TRIGGER] trg_sale_item_decrease_stock (AFTER INSERT)
   │     │           ├─► Verifica stock suficiente
   │     │           ├─► UPDATE inventory SET stock = stock - quantity
   │     │           └─► INSERT inventory_movements (type='exit', reason='Venta realizada')
   │     │
   │     ├─► autoCreateInvoice()
   │     │     ├─► Enrich client data (nombre, documento, email desde clients)
   │     │     ├─► Enrich seller data (nombre desde users)
   │     │     └─► INSERT invoice (ncf=null, status='issued')
   │     │
   │     └─► Publish SaleCreatedEvent + SaleCompletedEvent
   │           └─► [Event Bus] Subscribers log the events
   │
   └─► Response: Sale data (200 OK)

2. GET /api/v1/invoices/:id
   │
   ├─► SupabaseInvoiceRepository.findById()
   │     ├─► SELECT invoice + client join
   │     ├─► SELECT sale_items WHERE sale_id = invoice.sale_id
   │     └─► SELECT sales (sale_number, status)
   │
   └─► Response: Invoice data with items (200 OK)
```
