# Revisión de Rendimiento y Optimizaciones

## Resumen

Este documento analiza el rendimiento actual del sistema, identifica **15 problemas** de rendimiento categorizados por severidad, y propone soluciones concretas con estimación de impacto.

## 1. Problemas Encontrados

### 1.1 🔴 CRÍTICOS — Impacto Inmediato

#### P1: Dashboard ejecuta 10 queries paralelas por carga

**Archivo:** `backend/services/report-service/src/repository/index.js`
**Método:** `getDashboardStats()`

```javascript
// ❌ 10 queries independientes — cada una es un roundtrip HTTP a Supabase
const [totalProducts, lowStock, outOfStock, totalSales, salesSumResult,
       todaySalesResult, totalClients, adminUsersResult, cashierUsersResult, totalUsers] = await Promise.all([
  this._supabase.from('products').select('id', { count: 'exact', head: true }).eq('status', 'active'),
  this._supabase.from('inventory').select('id', { count: 'exact', head: true }).lte('stock', 5).gt('stock', 0),
  this._supabase.from('inventory').select('id', { count: 'exact', head: true }).eq('stock', 0),
  this._supabase.from('sales').select('id', { count: 'exact', head: true }),
  this._supabase.from('sales').select('total').gte('created_at', startOfMonth),
  this._supabase.from('sales').select('total').gte('created_at', today),
  this._supabase.from('clients').select('id', { count: 'exact', head: true }),
  this._supabase.from('users').select('id, roles!inner(name)', ...).eq('roles.name', 'admin'),
  this._supabase.from('users').select('id, roles!inner(name)', ...).eq('roles.name', 'cajero'),
  this._supabase.from('users').select('id', { count: 'exact', head: true }).eq('is_active', true),
]);
```

**Problema:** Aunque `Promise.all` corre en paralelo, son **10 roundtrips HTTP** a Supabase. Cada llamada tiene latencia de red (~5-20ms). En total: ~50-200ms solo para el dashboard. A medida que crecen los datos, los counts se vuelven más lentos.

**Solución:** Crear una función SQL en Supabase que devuelva todo en una sola llamada:

```sql
CREATE OR REPLACE FUNCTION fn_get_dashboard_stats()
RETURNS JSON AS $$
DECLARE
  result JSON;
BEGIN
  SELECT json_build_object(
    'total_products', (SELECT COUNT(*) FROM products WHERE status = 'active'),
    'low_stock', (SELECT COUNT(*) FROM inventory WHERE stock <= 5 AND stock > 0),
    'out_of_stock', (SELECT COUNT(*) FROM inventory WHERE stock = 0),
    'total_sales', (SELECT COUNT(*) FROM sales),
    'month_sales', COALESCE((SELECT SUM(total) FROM sales WHERE created_at >= date_trunc('month', NOW())), 0),
    'today_sales', COALESCE((SELECT SUM(total) FROM sales WHERE created_at >= CURRENT_DATE), 0),
    'total_clients', (SELECT COUNT(*) FROM clients),
    'total_users', (SELECT COUNT(*) FROM users WHERE is_active = true),
    'admin_users', (SELECT COUNT(*) FROM users u JOIN roles r ON u.role_id = r.id WHERE r.name = 'admin' AND u.is_active = true),
    'cashier_users', (SELECT COUNT(*) FROM users u JOIN roles r ON u.role_id = r.id WHERE r.name = 'cajero' AND u.is_active = true)
  ) INTO result;
  RETURN result;
END;
$$ LANGUAGE plpgsql STABLE;
```

**Ganancia:** 10 queries → **1 query**. ~80% menos latencia.

#### P2: `getClientReport()` carga TODOS los clientes sin paginación

**Archivo:** `backend/services/report-service/src/repository/index.js`
**Método:** `getClientReport()`

```javascript
// ❌ CARGA TODOS los clientes con TODAS sus ventas en una sola query
let query = this._supabase.from('clients').select('*, sales(id, total, created_at)');
```

```javascript
async getClientReport({ start_date, end_date, page = 1, limit = 20 }) {
  const from = (page - 1) * limit;
  // Usar subquery con filtro de fecha primero
  let query = this._supabase
    .from('clients')
    .select('id, name, email, phone', { count: 'exact' });
  // ... luego obtener ventas en query separada con filtro
```

#### P3: `getTopProducts()` carga TODOS los sale_items sin filtro de fecha obligatorio

**Archivo:** `backend/services/report-service/src/repository/index.js`
**Método:** `getTopProducts()`

```javascript
// ❌ Sin start_date/end_date, carga TODOS los items de venta
let itemsQuery = this._supabase
  .from('sale_items')
  .select('product_id, products(name, sku, price), quantity, total, sales(created_at)');
```

**Problema:** `sale_items` es la tabla que más crece (cada venta = N items). Sin límite de fechas, esta query se vuelve imposible con el tiempo.

**Solución:** Hacer obligatorio el rango de fechas y usar una función SQL con agregación:

```sql
CREATE OR REPLACE FUNCTION fn_get_top_products(
  p_start_date DATE DEFAULT CURRENT_DATE - INTERVAL '30 days',
  p_end_date DATE DEFAULT CURRENT_DATE,
  p_limit INTEGER DEFAULT 10
)
RETURNS TABLE(product_id UUID, name VARCHAR, sku VARCHAR, total_quantity BIGINT, total_revenue NUMERIC, order_count BIGINT) AS $$
BEGIN
  RETURN QUERY
  SELECT si.product_id, p.name, p.sku,
    SUM(si.quantity)::BIGINT,
    SUM(si.total)::NUMERIC,
    COUNT(DISTINCT si.sale_id)::BIGINT
  FROM sale_items si
  JOIN products p ON p.id = si.product_id
  JOIN sales s ON s.id = si.sale_id
  WHERE s.created_at >= p_start_date AND s.created_at <= p_end_date
  GROUP BY si.product_id, p.name, p.sku
  ORDER BY SUM(si.quantity) DESC
  LIMIT p_limit;
END;
$$ LANGUAGE plpgsql STABLE;
```

### 1.2 🟡 ALTOS — Impacto Significativo

#### P4: `autoCreateInvoice()` hace 4 queries secuenciales

**Archivo:** `backend/services/sale-service/src/usecases/index.js`
**Método:** `autoCreateInvoice()`

**Problema:** El método hace 4 queries en secuencia (esperando cada una):
1. `SELECT client` (si hay clientId)
2. `SELECT user` (seller name)
3. `SELECT last invoice` (para generar número)
4. `INSERT invoice`

**Solución:** Combinar client + user en paralelo usando `Promise.all()`, y usar RPC para el número secuencial:

```javascript
// ✅ Queries en paralelo
const [clientResult, userResult] = await Promise.all([
  clientId ? supabase.from('clients').select('...').eq('id', clientId).maybeSingle() : Promise.resolve({ data: null }),
  userId ? supabase.from('users').select('name').eq('id', userId).maybeSingle() : Promise.resolve({ data: null }),
]);

// Número de factura vía RPC (más rápido que SELECT + cálculo en Node)
const { data: invoiceNumber } = await supabase.rpc('generate_invoice_number');
```

**Ganancia:** 4 queries secuenciales → **2 paralelas + 1 RPC** (~50% menos tiempo).

#### P5: `findById()` en invoice-service hace 3 queries separadas

**Archivo:** `backend/services/invoice-service/src/repository/index.js`

```javascript
// ❌ 3 queries HTTP a Supabase
const { data } = await supabase.from('invoices').select('*, clients(...)').eq('id', id);
const { data: saleItems } = await supabase.from('sale_items').select('*').eq('sale_id', data.sale_id);
const { data: saleData } = await supabase.from('sales').select('sale_number, status').eq('id', data.sale_id);
```

**Solución:** Usar `SELECT` con join y el `!inner` hint para combinar:

```javascript
// ✅ Single query con left joins  
const { data } = await supabase
  .from('invoices')
  .select('*, clients(...), sales!inner(sale_number, status), sale_items(*, products(name, sku))')
  .eq('sales.id', supabase.rpc('get_sale_id_from_invoice', { p_invoice_id: id }))  // No, mejor:
  .eq('id', id);
```

**Solución práctica:** Crear una función RPC `fn_get_invoice_detail(p_invoice_id UUID)` que devuelva el invoice completo con items en una sola llamada.

**Ganancia:** 3 queries → **1 query**. ~30% menos tiempo en el endpoint más usado.

#### P6: `save()` en sale-service hace `findById()` redundante

**Archivo:** `backend/services/sale-service/src/repository/index.js`

```javascript
async save(sale) {
  const { data, error } = await supabase.from('sales').insert(persistence).select().single();
  // ... insert items ...
  return this.findById(data.id);  // ❌ Query pesada con 4 joins innecesaria
}
```

**Problema:** `save()` inserta la venta y luego ejecuta `findById()` que hace una query pesada con `clients(*)`, `users(name)`, `sale_items(*, products(*))`. El mapper podría construir el objeto de retorno desde `data` + `itemsData`.

**Solución:** Construir el return sin llamar a `findById()`:

```javascript
async save(sale) {
  const { data, error } = await supabase.from('sales').insert(persistence).select().single();
  if (error) throw error;
  // Insert items
  if (sale.items?.length) {
    const { error: itemsError } = await supabase.from('sale_items').insert(itemsData);
    if (itemsError) throw itemsError;
  }
  // ✅ En lugar de findById, construir mapper con menos joins
  return SaleMapper.toDomain({ ...data, sale_items: sale.items.map(i => i.toJSON()) });
}
```

**Ganancia:** Elimina 1 query pesada por cada venta creada.

#### P7: `updateStatus()` siempre hace `findById()` redundante

**Archivos múltiples:** `sale-service`, `invoice-service`, `inventory-service`

```javascript
async updateStatus(id, status, extraFields) {
  await supabase.from('sales').update({ status, ... }).eq('id', id);
  return this.findById(id);  // ❌ SELECT innecesario si el cliente no necesita el objeto completo
}
```

**Solución:** Retornar solo si el controller realmente necesita el objeto completo. En muchos casos, el status update no necesita devolver el objeto:

```javascript
// Opción 1: Parámetro opcional
async updateStatus(id, status, extraFields, returnFull = false) {
  await supabase.from('sales').update({ status, ... }).eq('id', id);
  return returnFull ? this.findById(id) : { id, status };
}
```

**Ganancia:** ~40ms por cada status update evitado.

### 1.3 🟡 MEDIOS — Impacto Moderado

#### P8: `getSalesChartData()` procesa datos en Node que SQL hace mejor

**Archivo:** `backend/services/report-service/src/repository/index.js`

**Problema:** Genera arrays de 24 horas y 28-31 días en JavaScript usando `Array.from` y bucles `forEach`, cuando SQL puede hacerlo con `date_trunc` y `generate_series`.

**Solución:**

```sql
-- Ventas por hora (hoy)
SELECT EXTRACT(HOUR FROM created_at)::INT AS hour,
  COUNT(*) AS count, SUM(total) AS total
FROM sales
WHERE created_at >= CURRENT_DATE
GROUP BY hour ORDER BY hour;
```

```sql
-- Ventas por día (mes actual)
SELECT DATE(created_at) AS date,
  COUNT(*) AS count, SUM(total) AS total
FROM sales
WHERE created_at >= DATE_TRUNC('month', NOW())
GROUP BY date ORDER BY date;
```

**Ganancia:** Menos datos transferidos (~24 filas vs procesar N ventas en Node) y sin lógica de fechas en JavaScript.

#### P9: `getInventoryReport()` hace nested join costoso

**Archivo:** `backend/services/report-service/src/repository/index.js`

```javascript
.select('*, products(id, name, sku, price, category_id, categories(name))')
```

**Problema:** Está trayendo `products.categories` dentro del join de inventory → products. Esto es un doble nested join en Supabase/PostgREST.

**Solución:** Separar en dos queries o usar un RPC:

```javascript
// Query 1: inventory + products
const { data: inventory } = await supabase
  .from('inventory')
  .select('*, products(id, name, sku, price, category_id)');
// Query 2: categories (cacheable, pocas filas)
const { data: categories } = await supabase
  .from('categories')
  .select('id, name');
// Mapear en Node
const categoryMap = Object.fromEntries(categories.map(c => [c.id, c.name]));
```

**Ganancia:** Evita el nested join lento, aprovecha cache de categorías (cambian poco).

#### P10: Falta de índices en columnas de filtro frecuente

**Análisis:** Las migraciones actuales no incluyen índigos en columnas críticas para reporting:

```sql
-- ❌ FALTAN estos índices:
CREATE INDEX IF NOT EXISTS idx_sales_created_at ON sales(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_sale_items_sale_id ON sale_items(sale_id);
CREATE INDEX IF NOT EXISTS idx_inventory_movements_created_at ON inventory_movements(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_inventory_movements_type ON inventory_movements(type, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_audit_logs_entity ON audit_logs(entity, entity_id);
CREATE INDEX IF NOT EXISTS idx_invoices_status ON invoices(status);
CREATE INDEX IF NOT EXISTS idx_invoices_sale_id ON invoices(sale_id);
```

**Impacto:** Todas las queries de reportes que filtran por `created_at` hacen **full table scan**. En tablas con 100K+ registros, la diferencia es de segundos.

**Solución:** Agregar estos índices en la próxima migración.

### 1.4 🔵 BAJOS — Impacto Menor pero Fáciles de Corregir

#### P11: Logger crea objeto en cada llamada aunque el nivel no coincida

**Archivo:** `backend/shared/utils/logger.js`

En todos los subscribers, los logs de `info` crean objetos `{ productId, warehouse }` incluso cuando el logger está configurado en `warn` o superior. Usar logger condicional o lazy evaluation.

---

#### P12: `revert_inventory_on_purchase_cancel()` no usa `FOR UPDATE`

**Archivo:** Base de datos (trigger)

En condiciones de concurrencia, dos cancelaciones simultáneas pueden causar inconsistencias. Todas las funciones que actualizan stock deberían usar `SELECT ... FOR UPDATE`.

---

#### P13: `createSupabaseClient()` se instancia por cada servicio

Cada microservicio crea su propia instancia de Supabase client. Aunque `@supabase/supabase-js` maneja connection pooling interno, tener 18 instancias separadas no es óptimo. **Sugerencia:** Usar una instancia compartida via el paquete `backend/shared/`.

---

#### P14: `getNextNumber()` en sale-service tiene fallback lento

```javascript
// Fallback: SELECT + cálculo en Node
const { data: lastSale } = await supabase.from('sales').select('sale_number')
  .order('created_at', { ascending: false }).limit(1).maybeSingle();
```

**Problema:** Cuando el RPC `generate_sale_number` falla, el fallback es lento. O el RPC funciona siempre o se necesita un mecanismo más robusto.

---

#### P15: Las fechas se serializan como string ISO en cada `toJSON()`

Los dominios (Sale, Invoice, etc.) convierten fechas a ISO string en cada `toJSON()` que se llama múltiples veces durante una request (mapper → controller → response). Cachear la serialización mejora el throughput.

## 4. Recomendaciones Arquitectónicas

### 4.1 Vista Materializada para Dashboard

Crear una vista materializada que se refresque cada 5 minutos para el dashboard:

```sql
CREATE MATERIALIZED VIEW IF NOT EXISTS mv_dashboard_stats AS
SELECT
  (SELECT COUNT(*) FROM products WHERE status = 'active') AS total_products,
  (SELECT COUNT(*) FROM inventory WHERE stock <= 5 AND stock > 0) AS low_stock,
  (SELECT COUNT(*) FROM inventory WHERE stock = 0) AS out_of_stock,
  (SELECT COUNT(*) FROM sales) AS total_sales,
  (SELECT COALESCE(SUM(total), 0) FROM sales WHERE created_at >= DATE_TRUNC('month', NOW())) AS month_sales,
  (SELECT COALESCE(SUM(total), 0) FROM sales WHERE created_at >= CURRENT_DATE) AS today_sales;

-- Refresh cada 5 minutos
SELECT cron.schedule('refresh-dashboard', '*/5 * * * *', 'REFRESH MATERIALIZED VIEW mv_dashboard_stats');
```

### 4.2 Migrar a RabbitMQ

El `InMemoryEventBus` actual pierde eventos si un servicio se reinicia. RabbitMQ daría:
- Persistencia de eventos
- Reintentos con backoff
- Mejor trazabilidad

### 4.3 Cache Distribuido (Redis)

Para datos de baja volatilidad:
- Catálogo de productos
- Categorías
- Configuración del sistema
- Precios

Redis reduciría ~40% de las queries a Supabase.
